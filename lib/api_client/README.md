# carnevale_api (EXPERIMENTAL)
Alongside these REST endpoints, a live game pushes updates over an ActionCable WebSocket at
`/cable` (`GameChannel`, subscribed with the `game_id`). Two event shapes travel on it:

- `{ \"event\": \"game_state\", \"game\": Game }` — the whole game, scoped to the receiving player's
  view (their own drawn agendas). Sent on subscribe and whenever something outside the models
  changes: a player joining, picking a gang, drawing/scoring/discarding an agenda, advancing or
  rewinding their turn, summoning or dismissing a model, or ending the game.
- `{ \"event\": \"entry_state\", \"player_id\": integer, \"list_entry_id\": integer, \"state\": EntryState,
  \"spell_casts\": { \"<spell key>\": boolean } }` — one model's changed state, sent by the five
  entry endpoints below (counters, stats, tokens, spell casts). Nothing in the `Game` payload is
  derived from a model's state, so these deliberately don't broadcast `game_state`: the change
  travels in the event itself and the client applies it to that one model rather than re-fetching
  both player lists to find what moved. `spell_casts` keys match the `key` on the entry's
  `pools[].spells`/`pools[].cantrips`/`granted_spells`; it rides alongside `state` because
  deriving `cast` needs each spell's `resets_each_round`, which the entry state alone doesn't
  carry. Both turn-derived flags (`state.activated` and `spell_casts`) resolve against the
  *owning* player's turn cursor, since each player advances turns independently.
